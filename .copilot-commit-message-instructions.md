# Copilot Commit Message Instructions

Use **Conventional Commits** for all commit messages in this repository.

## Format

```text
<type>(<optional-scope>): <short imperative summary>

<optional body>

<optional footer>
```

## Allowed types

- `feat`: new feature (triggers **minor** release)
- `fix`: bug fix (triggers **patch** release)
- `docs`: documentation only
- `style`: formatting only (no logic changes)
- `refactor`: code change without feature/fix
- `perf`: performance improvement
- `test`: add/update tests
- `build`: build system or dependencies
- `ci`: CI/CD workflow changes
- `chore`: maintenance tasks
- `revert`: reverts a previous commit

## Breaking changes

For breaking changes, use one of the following:

- Add `!` after type/scope, e.g. `feat(api)!: remove v1 endpoints`
- Or include `BREAKING CHANGE:` in the footer

This triggers a **major** release.

## Subject line rules

- Imperative mood: "add", "fix", "update" (not "added" or "fixes")
- Lowercase type and scope
- Keep summary concise (prefer <= 72 chars)
- No trailing period

## Scope guidance

Use a scope when it improves clarity, such as:

- `ci`, `release`, `workflow`
- `ui`, `pdf`, `xml`, `i18n`
- `docs`, `deps`

## Good examples

- `feat(ui): add export overlay loading state`
- `fix(pdf): prevent empty answer sections in export`
- `ci(workflows): validate commit messages with commitlint`
- `docs(readme): explain release and deploy flow`
- `feat(xml)!: change schema for imported answers`

## Bad examples

- `updated stuff`
- `Fix bug.`
- `feat: added new feature`
- `minor changes`

## Notes for Copilot-generated commits

- Prefer one logical change per commit.
- Choose `feat` or `fix` only when appropriate for release impact.
- Use `ci` for `.github/workflows/*` changes.
- Use `docs` for README or documentation-only changes.
